# Vector Clock

[Lamport clock](chunk://lamport-clock) 一個節點只記一個數字，所以拿到兩個數字，分不出這兩件事是一前一後，還是各做各的。Vector clock 改成每個節點記一排數字，一格對應一個節點。

三個節點 A、B、C，每個節點手上一開始都是 [A:0, B:0, C:0]。自己做一件事，就把自己那格加一。送訊息也算一件事，所以先把自己那格加一，再把加完的整排附上。收到訊息時，每一格各取雙方的最大值，然後再把自己那格加一。

還是訂單系統。A 下單、B 扣庫存、C 算推薦，C 跟這筆訂單沒有關係。

```text
A 下單                                  A: [A:1, B:0, C:0]
A 送訊息給 B，A 那格先加一，附上整排      A: [A:2, B:0, C:0]
B 收到，逐格取 max，再把 B 那格加一        B: [A:2, B:1, C:0]
B 扣庫存                                 B: [A:2, B:2, C:0]
C 自己算推薦，沒跟任何人講話              C: [A:0, B:0, C:1]
```

比較兩排數字。A 下單是 [1,0,0]，B 扣庫存是 [2,2,0]，每一格前者都 ≤ 後者，所以下單發生在扣庫存之前。B 扣庫存 [2,2,0] 跟 C 推薦 [0,0,1] 就不一樣了，B 那排的 A 格比較大，C 那排的 C 格比較大，互相都不包含，這兩件事就是 concurrent，誰也不在誰前面。同一個情境換成 Lamport clock：A 下單 1、送出 2，B 收到是 max(0, 2) + 1 = 3、扣庫存 4，C 推薦 1。B 拿到 4、C 拿到 1，看起來 C 先，其實兩邊沒有關係。

落到資料庫裡，concurrent 就是同一個 key 被兩個節點各改了一版，兩版帶的向量互不包含，系統沒辦法自己挑一版，要嘛把兩版都留下來交給上層合併，要嘛訂一條規則挑。Amazon 2007 年的 Dynamo 論文用的就是這套。後來的 DynamoDB 服務換了做法，每個 partition 只有 leader 那台收寫入，所以在單一 region 裡，同一個 key 不會被兩個節點各改一版。跨 region 的 global tables 才會出現兩版，在最終一致（MREC）模式下用 last writer wins，挑 DynamoDB 內部 timestamp 最新的那版。

代價在向量本身。向量裡記的是改過這筆資料的節點，改過的節點越多，向量越長，跟 cluster 總共幾台無關。Dynamo 一筆資料平常由 preference list 前 N 台處理，論文裡常見的設定是 N = 3，所以向量通常只有幾格。網路分區或多台故障時，其他節點接手寫入，向量才會變長，論文的做法是格數到了 10 就把最舊的那格丟掉；丟掉之後，有些版本就分不出誰在誰前面了。
