# STUN / TURN

> 兩個瀏覽器都在 NAT 後面，沒有公開地址，WebRTC 要直連，地址從哪來？

先講 NAT 做了什麼。家裡的筆電 IP 是 192.168.1.5，這個地址只在家裡的網路有效。筆電從 port 50000 往外送一個封包，路由器把來源改寫成自己的公開地址 203.0.113.7，port 改成 40001，並且記一筆「40001 對應 192.168.1.5:50000」。外面回來送到 203.0.113.7:40001 的封包，路由器查表後轉回筆電。表上沒有的封包，路由器直接丟掉。所以筆電自己不知道 203.0.113.7:40001 這個地址，對方也沒辦法主動連進來。

## STUN：查出自己的公開地址

STUN server 架在公網上。筆電送封包過去，它看封包的來源是哪個地址跟 port，原樣回覆。筆電 A 問到自己是 203.0.113.7:40001，另一邊的筆電 B 問到自己是 198.51.100.9:62000。兩邊透過 signaling server 交換這兩個地址，然後同時往對方送封包。A 一送往 198.51.100.9:62000，A 的路由器就記下「40001 可以收來自 198.51.100.9:62000 的回覆」，B 那邊也一樣。接著 B 送來的封包到 A 的路由器，表上有紀錄，放行。這一招英文叫 hole punching。多數家用路由器這樣就能直連。

STUN 給完地址就退場，媒體流不經過它。

## TURN：直連失敗時的中繼

有一種路由器叫對稱型 NAT，每換一個目標就換一個對外 port。A 問 STUN 時用的是 40001，等 A 改送給 B，路由器換成 40002。B 手上拿的還是 40001，送過去，A 的路由器表上 40001 對應的目標是 STUN server，不是 B，封包被丟掉。直連失敗。

這時退到 TURN。TURN server 也在公網上，A 向它要一個中繼地址，拿到 203.0.113.50:49200，交給 B。之後 B 送到那裡，TURN 轉給 A；A 送給 TURN，TURN 轉給 B。兩邊都只跟 TURN 講話，不需要對方的路由器放行。

代價是 TURN 全程留在資料路徑上，一路視訊的每個封包都經過它，頻寬跟機器都是錢。callstats.io 在 [webrtcHacks 發表的統計](https://webrtchacks.com/usage-stats/)涵蓋 2015 年 1 月到 2016 年 2 月、數十億分鐘的通話，裡面 22% 的會議需要某種 TURN 中繼。
