# Sealed Secrets

GitOps wants every piece of configuration in Git, but a secret in plain text cannot go there. The two requirements collide head on.

## The problem

The DB password is `s3cr3t`. Written as a k8s Secret, the YAML stores the base64 form, `czNjcjN0`. base64 is not encryption. Anyone who clones the repo runs one line, `echo czNjcjN0 | base64 -d`, and sees `s3cr3t`. Putting the Secret YAML in Git hands the password to everyone with access to the repo.

But if the Secret is not in Git, how does ArgoCD sync it? Run `kubectl create secret` by hand? That breaks the GitOps idea that Git is the single source of truth.

## How Sealed Secrets solves it

Bitnami Sealed Secrets runs a controller inside the cluster. The controller generates a key pair: the private key stays in the cluster, the public key can be given to anyone.

Walk the same password through:

1. An engineer encrypts on their own machine with `kubeseal`. `kubeseal` asks the cluster for the public key, encrypts `s3cr3t` into a long ciphertext, and produces a SealedSecret YAML.
2. The SealedSecret YAML is committed to Git. It contains only the ciphertext; anyone who clones the repo sees noise, and without the private key it cannot be opened.
3. ArgoCD syncs the SealedSecret into the cluster.
4. The controller in the cluster sees the new SealedSecret, decrypts it with the private key, and produces a real k8s Secret containing `s3cr3t`, which the app mounts as usual.

The private key lives in a Secret inside the cluster, and Git holds only the ciphertext, so someone who clones the repo cannot decrypt it. A new cluster gets a new private key, generated by its own controller, and the old ciphertext in Git cannot be opened there. So the private key needs its own backup. The official README gives the command `kubectl get secret -n kube-system -l sealedsecrets.bitnami.com/sealed-secrets-key -o yaml >main.key`; after rebuilding the cluster, run `kubectl apply -f main.key` before starting the controller. By default the controller adds a new private key every 30 days. The old keys stay and still decrypt old ciphertext, but the new key is not in the old backup, so every new key needs a fresh backup.

## Other approaches

- **SOPS**: Mozilla's encryption tool, which encrypts the values inside a YAML with AWS KMS / GCP KMS / age / PGP. Not limited to k8s, the most flexible in formats and key sources, at the cost of more setup.
- **External Secrets Operator (ESO)**: pulls secrets from Vault / AWS Secrets Manager on demand and syncs them into k8s Secrets, nothing stored in Git. Supports automatic rotation and multiple providers.
- **HashiCorp Vault**: centralized secret management, accessed through an API.

For a small team and a simple setup, Sealed Secrets is the least work; at scale, with automatic rotation and an external secret store to connect, ESO is the more common choice today.
