# Blob Storage

> 使用者上傳的圖片、影片、備份檔，總不會一股腦塞進資料庫吧？

## 用 key 存大檔案

blob storage（物件儲存）專門放大的、非結構化的檔案。S3、GCS、Azure Blob 是代表。

走一遍上傳頭像。使用者 123 上傳一張 4MB 的照片。app 不把這 4MB 寫進資料庫，而是用 HTTP PUT 把檔案送到 bucket `avatars`，key 取 `users/123/avatar.jpg`。資料庫的 users 表只多一欄，存這個 key 或完整 URL，一列幾十 bytes。前端要顯示頭像，拿到 URL 直接向 CDN 要，CDN 第一次向 bucket 拉，之後就從自己那邊回，app server 跟資料庫都沒有經手這 4MB。

key 裡的 `/` 看起來像資料夾，其實不是。bucket 是一個扁平的 key 空間，`users/123/avatar.jpg` 就是一整串字，沒有一個叫 `users` 的目錄存在。列出「users/123/ 底下有什麼」，是用前綴去篩 key。因為物件不可變，使用者換頭像時只能把整張圖重新上傳，不能只改檔案的某一段。要是新圖用同一個 key 覆蓋，CDN 手上那份舊圖不會跟著失效，要等它的 cache 過期（CloudFront 預設 24 小時）或有人手動 invalidation，這段時間別人看到的還是舊頭像。所以新圖通常換一個 key，例如 `users/123/avatar-v2.jpg`，資料庫那一欄改存新 key，前端拿到的就是一個 CDN 沒看過的 URL。

像一個超大寄物櫃，每個櫃子一個號碼牌（key），放大件行李很便宜也很耐放，但每天要翻好幾次的小東西不會放在這裡。

## 為什麼這麼耐放

背後用 erasure coding。舉例，把一個物件切成 10 片，再算出 4 片冗餘碼，14 片分散放在 14 顆不同的磁碟，甚至不同機房。任何 10 片都能還原整個物件，所以同時壞 4 顆磁碟也沒事。要是改用複製三份，容量要花三倍，壞 2 顆就到極限；10 + 4 只花 1.4 倍，還能多壞 2 顆。S3 標稱 11 個 9，一年弄丟一個物件的機率小到可以忽略。

代價是單個物件的存取延遲比 DB 高，也沒有部分更新，所以不適合高頻交易型資料，適合圖片、影片、備份這類寫一次、讀很多、不常改的資料。
