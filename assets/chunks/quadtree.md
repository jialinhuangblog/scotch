# Quadtree（四叉樹）

> [Geohash](chunk://geohash) 把地圖切成一樣大的格子。但市中心一格塞一萬家店、海面一格空無一物，同一種格子大小顯然不合理。Quadtree 讓密的地方切細、疏的地方留大格。

## 機制：擠了就切四份

一開始整張地圖是一格。一格裡的點超過容量（例如 100 個），就把它切成四個象限。切完還是擠，那一格再切四份。遞迴下去。

```text
整張地圖一格
  ┌───────────┐
  │           │   點 > 100 → 切四份
  └───────────┘
        ↓
  ┌─────┬─────┐
  │ 稀疏 │ 稠密 │  右上又 > 100 → 只有它再切
  ├─────┼──┬──┤
  │     │  │  │
  └─────┴──┴──┘
```

結果是一棵樹：稠密區的葉子又小又深，稀疏區的葉子又大又淺。格子大小跟著點的密度自己長，這叫 adaptive（自適應），是它跟 geohash 最大的不同。

## 查詢：從 root 往下砍

「找這個矩形範圍內的點」：從最上層那格開始，只往下走跟查詢範圍有重疊的子格，沒重疊的整棵子樹直接跳過。像 [B-tree](chunk://b-tree) 砍範圍，只是砍的是二維空間。

## 跟 geohash 差在哪

| | geohash | quadtree |
|---|---|---|
| 格子大小 | 固定，一種 precision 一種大小 | 自適應，跟著密度變 |
| 資料結構 | 字串 prefix，可直接進 B-tree | 一棵樹，要自己維護 |
| 點分佈很不均 | 稀疏區浪費格子、稠密區塞爆 | 天生擅長 |
| 存進 SQL | 容易（就是個字串欄位） | 難（樹狀，通常在記憶體或專用 index） |

所以 geohash 贏在「一個字串搞定、直接 index」，quadtree 贏在「密度差很大時不浪費」。

## 誰在用

碰撞偵測（遊戲裡只檢查同格附近的物件）、圖像壓縮、早期的地圖服務。DB 層是另一回事：PostGIS 的空間 index 用的是 [R-tree](chunk://geohash)（bounding box 樹）不是 quadtree，兩者是概念鄰居，都靠「空間分層、查詢時砍不相干的區域」，實作細節不同。

---

Quadtree 把空間遞迴切四份，密的地方切細、疏的地方留大格。贏在點分佈不均時不浪費，代價是它是一棵要維護的樹，不像 geohash 一個字串就能塞進 DB。
