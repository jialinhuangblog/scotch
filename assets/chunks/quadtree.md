# Quadtree（四叉樹）

> [Geohash](chunk://geohash) 把地圖切成一樣大的格子。但市中心一格塞一萬家店、海面一格空無一物，同一種格子大小顯然不合理。Quadtree 讓密的地方切細、疏的地方留大格。

## 機制：擠了就切四份

一開始整張地圖是一格。一格裡的點超過容量（例如 100 個），就把它切成四個象限。切完還是擠，那一格再切四份。遞迴下去。

```text
整張地圖一格
  ┌───────────┐
  │           │   點 > 100 → 切四份
  └───────────┘
        ↓
  ┌─────┬─────┐
  │ 稀疏 │ 稠密 │  右上又 > 100 → 只有它再切
  ├─────┼──┬──┤
  │     │  │  │
  └─────┴──┴──┘
```

結果是個樹狀結構，稠密區的 leaf 又小又深，稀疏區的 leaf 又大又淺。格子大小會跟著點的密度變，這叫 adaptive（自適應），也是它跟 geohash 最大的不同。

## 查詢：只走有重疊的子格

「找這個矩形範圍內的點」：從最上層那格開始，只往下走跟查詢範圍有重疊的子格，沒重疊的子樹直接跳過。跟 [B-tree](chunk://b-tree) 排除不相干範圍的做法一樣，只是換成二維空間。

## 跟 geohash 差在哪

| | geohash | quadtree |
|---|---|---|
| 格子大小 | 固定，一種 precision 一種大小 | 自適應，跟著密度變 |
| 資料結構 | 字串 prefix，可直接進 B-tree | 樹狀結構，要自己維護 |
| 點分佈很不均 | 稀疏區浪費格子、稠密區擠滿 | 天生擅長 |
| 存進 SQL | 容易（就是個字串欄位） | 難（樹狀，通常在記憶體或專用 index） |

## 誰在用

碰撞偵測（遊戲裡只檢查同格附近的物件）、圖像壓縮、早期的地圖服務。DB 層是另一回事：PostGIS 的空間 index 用的是 R-tree（把相鄰的物件用 bounding box 框起來，一層一層往上包成樹），不是 quadtree。兩者概念相近，都靠「空間分層、查詢時跳過不相干的區域」，實作細節不同。
