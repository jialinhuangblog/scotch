# Consistent Hashing

> 通用概念。Cassandra、DynamoDB、Memcached、Nginx 都用這個方法把資料分配到多台機器。

## 先想一個場景

有一個電商網站，商品頁面很慢，決定加 cache。買了 3 台 Redis server，分別叫 S0、S1、S2。

問題來了：商品 A 的 cache 應該放在哪一台？

### 最直覺的做法

對商品 ID 做 hash，除以機器數量取餘數。

```text
hash("商品A") = 108  →  108 % 3 = 0  →  放 S0
hash("商品B") = 211  →  211 % 3 = 1  →  放 S1
hash("商品C") = 315  →  315 % 3 = 0  →  放 S0
hash("商品D") = 427  →  427 % 3 = 1  →  放 S1
hash("商品E") = 550  →  550 % 3 = 2  →  放 S2
hash("商品F") = 633  →  633 % 3 = 0  →  放 S0
```

讀取時用同樣的公式算，就知道去哪台拿。簡單，能用。

### 雙十一流量暴增，加一台 server

S3 上線。機器數量從 3 變成 4。公式變成 `% 4`。

```text
hash("商品A") = 108  →  108 % 4 = 0  →  S0 (沒變)
hash("商品B") = 211  →  211 % 4 = 3  →  S3 (原本在 S1！)
hash("商品C") = 315  →  315 % 4 = 3  →  S3 (原本在 S0！)
hash("商品D") = 427  →  427 % 4 = 3  →  S3 (原本在 S1！)
hash("商品E") = 550  →  550 % 4 = 2  →  S2 (沒變)
hash("商品F") = 633  →  633 % 4 = 1  →  S1 (原本在 S0！)
```

6 個商品，4 個搬家了。cache 裡的資料還在舊機器上，但公式指向新機器，結果是 cache miss。大量 miss 湧進 DB，DB 一下子吃不消。

加機器是為了撐住流量，結果反而引發更大的流量衝擊。

3 台變 4 台，平均 75% 的 key 要重新分配。100 台變 101 台，99% 要重新分配。機器越多，加一台的代價越大。

### 有沒有辦法讓 N 不出現在除數裡？

有。這就是 consistent hashing 要解決的問題。

## 把直線變成一個環

`% N` 的問題在於：分母變了，所有結果都變。如果不除以 N 呢？

想像 hash 值的範圍是 0 到 999，頭尾相接形成一個環。3 台機器各自算一個 hash，落在環上的某個位置。

```text
            0
      ┌─────┴─────┐
  S0 (100)         │
      │            │
      │        S1 (400)
      │            │
  S2 (900)         │
      └─────┬─────┘
           600
```

S0 在位置 100，S1 在位置 400，S2 在位置 900。

每個商品也算 hash，落在環上某個位置。然後順時針走，碰到的第一台 server 就是負責它的 server。

```text
商品A hash=250  → 順時針走 → 碰到 S1(400)  → 放 S1
商品B hash=500  → 順時針走 → 碰到 S2(900)  → 放 S2
商品C hash=950  → 順時針走 → 繞過 0 → 碰到 S0(100)  → 放 S0
```

### 現在加一台 S3 在位置 300

```text
            0
      ┌─────┴─────┐
  S0 (100)         │
      │            │
  S3 (300) ← 新   │
      │        S1 (400)
      │            │
  S2 (900)         │
      └─────┬─────┘
           600
```

S3 插在 S0 和 S1 之間。影響了誰？

- hash 值在 100~300 之間的商品，原本順時針會碰到 S1，現在先碰到 S3。這些要搬。
- 其餘所有商品，順時針碰到的 server 沒變。不用搬。

商品A hash=250，原本 → S1，現在 → S3。要搬。
商品B hash=500，原本 → S2，現在 → S2。不動。
商品C hash=950，原本 → S0，現在 → S0。不動。

加一台機器，只有落在 S3 前一段弧上的 key 需要搬。搬遷量從 75% 降到大約 1/N。

### 移除一台呢？

S1 掛了。S1 負責的那段弧（300~400）上的 key，順時針找不到 S1，會找到下一台 S2。只有 S1 上的資料需要搬到 S2。其餘不動。

## 新的問題：分配不均

三台機器剛好均勻地分在環上，每台負責 1/3 的弧，是理想情況。

現實中 hash 是隨機的。可能 S0 在 100、S1 在 150、S2 在 900。S2 負責從 150 到 900 這一大段，佔了 75% 的 key。S0 和 S1 加起來才 25%。

```text
S0(100)  S1(150)                              S2(900)
  |--------|------- 這一大段全歸 S2 ------------|
  很短很短                 超長
```

### Virtual Nodes 怎麼解決

不要只放一個點。把每台實體 server 拆成很多個「虛擬節點」，散佈在環上。

S0 拆成 S0-a、S0-b、S0-c... 放在環上 150 個不同的位置。S1、S2 也一樣。

```text
環上：S0-a, S1-c, S2-b, S0-d, S2-a, S1-b, S0-c, S1-a, S2-d ...
```

3 台實體機器，每台 150 個 virtual nodes，環上就有 450 個點。點越密，每台分到的弧長越接近 1/3。

為什麼點多就均勻？想像丟骰子。丟 3 次，可能出現 1, 1, 6，分佈很歪。丟 450 次，平均值逼近 3.5。大數法則。一台只有 1 個點，那個點落在哪，就決定了它分到多長一段。150 個點散在各處，長段和短段互相抵消，總量趨近 1/N。

```text
3 個點（每台 1 個）：

        0
  ┌─────┴─────┐
S0(100)        │       S0：900→100 (20%)
S1(150)        │       S1：100→150 (5%)
  │            │       S2：150→900 (75%) ← 慘
S2(900)        │
  └─────┬─────┘

9 個點（每台 3 個）：

        0
  ┌─────┴─────┐
S0-a(100)      │       S0 的 3 段弧加起來 ≈ 33%
  │    S1-a(200)       S1 的 3 段弧加起來 ≈ 33%
S2-a(300)      │       S2 的 3 段弧加起來 ≈ 33%
  │    S0-b(450)
S1-b(550)      │       每台散成多段，長短互相抵消
  │    S2-b(650)
S0-c(750)      │
  │    S1-c(880)
  └─────┬─────┘
```

Cassandra 預設每個節點 256 個 virtual nodes。

Virtual node 數量也是控制「每台實體機器分多少比例流量」的一個設定。Virtual node 多 = 那台機器在環上佔的弧加總更長 = 更多 key 被路由到那台機器。所以硬體比較強的機器（CPU 多、RAM 大），可以給它更多 virtual nodes，讓它承擔更多 key。

---

`hash % N` 加一台機器要搬幾乎全部資料。Consistent hashing 把 hash 空間變成環，加減機器只影響相鄰的一小段。Virtual nodes 讓分配更均勻。
